# Мониторинг, логирование и оповещение — обоснование решения

## 1. Выбранный способ доставки и альтернативы

Выбранный способ доставки — **Micrometer + Spring Boot Actuator**, эндпойнт `/actuator/prometheus`. Используется pull-модель - Prometheus сам скрейпит приложение раз в 5 секунд. Micrometer интегрирован в Spring Boot «из коробки» (одна зависимость `micrometer-registry-prometheus`), даёт более осмысленные метрики уровня приложения (`spring.batch.*`, HTTP-метрики) и не требует конфигурации отдельного Java-агента в `Dockerfile`/команде запуска.

### Альтернативы
**JMX Exporter.** Отдельный Java-агент, который подключается к JVM через JMX и транслирует MBeans в формат Prometheus. Для Spring Boot-приложения это лишний слой, низкоуровневые JVM MBeans.

**Prometheus Agent (remote-write).** Режим самого Prometheus для пересылки метрик в удалённое хранилище (актуально для мульти-кластерных/облачных инсталляций с центральным Prometheus/Thanos/Mimir). У нас один локальный Prometheus и одно приложение — pull-скрейпинг стандартного `/actuator/prometheus` проще, не требует лишнего компонента.

**Метрики и их описание:**

| Метрика | Зачем |
| :- | :- |
| `up{job="batch-processing"}` | Признак «жив ли процесс» — без него нет ни дашбордов, ни алертов |
| `spring_batch_job_seconds_count{status=...}` | Метрика бизнес-события: сколько раз и с каким статусом (`COMPLETED`/`FAILED`) отработал ETL Job|
| `process_cpu_usage` | Показатель нагрузки на процесс — пригодится, когда объём данных вырастет до 400 000+ строк/сутки |
| `jvm_memory_used_bytes{area="heap"}` | Chunk-обработка держит данные чанками в памяти — рост потребления памяти сигнализирует о слишком большом `chunk size` или утечке до того, как приложение упадёт с `OutOfMemoryError` |

## 2. Обоснование выбора стека для логов: Filebeat → Logstash → Elasticsearch

Альтернативы, которые не выбрали:
- **Прямая отправка логов из приложения в Logstash/Elasticsearch** (TCP/HTTP-аппендер в `logback`) — работает, но привязывает код приложения к конкретному приёмнику логов; если Elasticsearch недоступен, можно потерять или заблокировать логирование в самом приложении. Filebeat читает уже записанные Docker-логами файлы — потеря приёмника не роняет и не тормозит приложение.
- **Fluentd/Fluent Bit** — сопоставимая альтернатива Filebeat, но Filebeat уже был в шаблоне задания и штатно интегрируется с остальным Elastic-стеком (тот же вендор, совместимые версии), не вижу причины менять.
- **Только `docker logs`/файлы без централизации** — не подходит по прямому требованию задания (централизованный сбор логов) и не масштабируется при 100–150 параллельных обработках, о которых говорится в кейсе — искать причину сбоя по логам одного контейнера вручную нереально.

**Почему именно эта связка:** Filebeat уже сконфигурирован читать `stdout` всех Docker-контейнеров хоста (`/var/lib/docker/containers`) — не нужно ничего монтировать/настраивать в самом приложении, кроме формата логов. Приложение при этом пишет не текстовые строки, а **структурированный JSON** (через `logstash-logback-encoder` в `logback-spring.xml`) — с полями `level`, `logger`, `msg`, `traceId`/`spanId`. Filebeat это распознаёт (`decode_json_fields`) и передаёт уже готовые поля, а не сырую строку — в Kibana можно фильтровать по `level: ERROR` или `logger`, а не парсить текст регулярками. Проверено вживую: логи `app` доходят до Elasticsearch с корректно распарсенными полями (см. `screenshots/kibana-logs.png`).

## 3. Алерты: почему Grafana Alerting, а не Prometheus + Alertmanager

В данном стеке не поднят отдельный Alertmanager — Grafana Alerting (начиная с Grafana 8, встроенный «unified alerting») умеет то же самое: оценивать PromQL-запросы по расписанию, хранить состояние (`Normal`/`Pending`/`Firing`), группировать и роутить уведомления через contact points — без дополнительного контейнера и его отдельной конфигурации маршрутизации. Для одного источника данных (Prometheus) и пары правил разворачивать ещё один сервис избыточно; Alertmanager был бы оправдан при нескольких Prometheus-инстансах или сложной маршрутизации оповещений между командами.

**Настроенные алерты (`screenshots/grafana-alert-rules.png`):**

1. **`App Down`** — `up{job="batch-processing"}` IS BELOW `1`. Самый базовый и самый важный алерт: если приложение недоступно, никакие остальные метрики уже не имеют значения — сотрудники склада не получат уведомление об обработке отчёта.
2. **`Batch Job Failed`** — `spring_batch_job_seconds_count{job="batch-processing", spring_batch_job_status!="COMPLETED"} > 0`. Отражает ровно ту проблему, из-за которой в кейсе TradeWare отчёты «висят» — Job либо завершился с ошибкой, либо не завершился успешно вовсе. Без этого алерта о сбое обработки узнали бы только по жалобе пользователей.

Оба правила проверены живьём в состоянии `Normal` (приложение работает, Job завершился успешно) — то есть логика условий корректна и не даёт ложных срабатываний на здоровой системе.
