# Обоснование выбора способа отправки логов и конфигурации оповещений

## 1. Выбор способа отправки логов

### Текущая ситуация

В исходной архитектуре TradeWare логирование ограничивалось записью в файлы на VM и стандартным мониторингом ресурсов. При возникновении ошибок в ETL-процессах команде приходилось вручную подключаться к серверу, искать нужный файл и анализировать логи — это медленно и неэффективно, особенно в пиковые периоды с 100+ параллельными загрузками.

### Рассмотренные варианты

| Критерий | Filebeat + Logstash + Elasticsearch | Fluentd + Elasticsearch | Promtail + Loki | Rsyslog + Graylog |
|----------|:---:|:---:|:---:|:---:|
| **Простота настройки** | 🟡 Средне | 🟡 Средне | ✅ Просто | ❌ Сложно |
| **Производительность** | ✅ Высокая | ✅ Высокая | ✅ Высокая | 🟡 Средняя |
| **Масштабируемость** | ✅ Отличная | ✅ Отличная | ✅ Хорошая | 🟡 Средняя |
| **Полнотекстовый поиск** | ✅ Elasticsearch | ✅ Elasticsearch | 🟡 Loki | ✅ Elasticsearch |
| **Визуализация (Kibana)** | ✅ Нативная | ✅ Через Kibana | ❌ Grafana only | 🟡 Свой UI |
| **Поддержка JSON-логов** | ✅ Отличная | ✅ Хорошая | ✅ Хорошая | 🟡 Средняя |
| **Потребление ресурсов** | 🟡 Среднее | 🟡 Среднее | ✅ Низкое | ❌ Высокое |
| **Совместимость с GCP** | ✅ Elastic Cloud / Self-hosted | ✅ GCP Marketplace | ✅ GKE | ❌ Нет managed-решения |
| **Экосистема Spring Boot** | ✅ Logstash Encoder | 🟡 Свой форматтер | 🟡 Через Logback | ❌ Требует адаптации |

### Выбранное решение: Filebeat + Logstash + Elasticsearch + Kibana (ELK Stack)

**Обоснование:**

1. **Нативная интеграция со Spring Boot.** Библиотека `logstash-logback-encoder` позволяет генерировать структурированные JSON-логи прямо из приложения без дополнительных парсеров на стороне Logstash.

2. **Полнотекстовый поиск.** Elasticsearch обеспечивает мгновенный поиск по всем полям логов — критически важно при отладке ETL-процессов, когда нужно найти конкретную ошибку среди миллионов записей.

3. **Kibana для визуализации.** Встроенные дашборды Kibana (Discover, Dashboard) позволяют быстро построить графики по логам без написания запросов — снижает порог входа для команды.

4. **Filebeat как лёгкий агент.** Filebeat потребляет минимум ресурсов (≈30MB RAM), что важно для контейнеризированной среды. Он отслеживает файлы логов и гарантирует доставку (at-least-once семантику) даже при перезапусках.

5. **Готовность к облачной инфраструктуре.** Elasticsearch можно развернуть как self-hosted в GKE или использовать Elastic Cloud на GCP Marketplace — миграция не потребует смены формата логов.

6. **Проверенное решение.** ELK Stack — индустриальный стандарт для централизованного логирования. Большое сообщество и документация снижают риски при внедрении.

7. **Горизонтальная масштабируемость.** При росте объёмов логов можно добавить Kafka между Filebeat и Logstash для буферизации, а Elasticsearch масштабируется добавлением нод.

### Отклонённые альтернативы

- **Fluentd:** более сложная конфигурация (требует понимания директив `<source>`, `<match>`, `<filter>`), меньше готовых интеграций с Java-экосистемой.
- **Loki:** проще и легче, но ограниченная функциональность поиска по сравнению с Elasticsearch, нет полноценной замены Kibana для не-Grafana пользователей.
- **Graylog:** требует отдельного MongoDB, более тяжёлый в эксплуатации, меньше сообщество.

## 2. Выбор способа отправки метрик

### Рассмотренные варианты

| Критерий | Micrometer + Prometheus Agent | JMX Exporter | Spring Boot Actuator + Telegraf | OpenTelemetry |
|----------|:---:|:---:|:---:|:---:|
| **Интеграция со Spring Boot** | ✅ Нативная | 🟡 Требует JMX-бина | 🟡 Дополнительный агент | 🟡 Новый SDK |
| **Формат метрик** | ✅ Prometheus | ✅ Prometheus | 🟡 InfluxDB/Prometheus | ✅ OTLP |
| **Богатство метрик из коробки** | ✅ JVM, HTTP, Batch | 🟡 Только JMX | ✅ Широкий охват | ✅ Полный трейсинг |
| **Влияние на приложение** | ✅ Минимальное | 🟡 JMX overhead | ❌ Отдельный процесс | 🟡 Новые зависимости |
| **Настройка дашбордов** | ✅ Готовые Grafana | 🟡 Ручная настройка | 🟡 Ручная настройка | 🟡 Jaeger/Grafana |

### Выбранное решение: Micrometer + Prometheus (через Actuator endpoint)

**Обоснование:**

1. **Micrometer — стандарт для Spring Boot.** Это библиотека, которая уже включена в Spring Boot Actuator. Она автоматически собирает метрики JVM (память, GC, потоки), HTTP-запросов, DataSource, а Spring Batch добавляет свои метрики через `JobExecutionListener` и `StepExecutionListener`.

2. **Prometheus endpoint из коробки.** Добавление зависимости `micrometer-registry-prometheus` автоматически создаёт endpoint `/actuator/prometheus`, который Prometheus может скрейпить. Не нужно настраивать JMX-бины или отдельные агенты.

3. **Минимальное влияние на производительность.** Micrometer использует in-memory регистр метрик, который не блокирует бизнес-логику. Скрейпинг Prometheus занимает миллисекунды.

4. **Богатый набор кастомных метрик.** Мы добавили специфичные для ETL метрики:
    - `batch.step.duration` — время выполнения шага (Timer)
    - `batch.step.read.count` — количество прочитанных записей (Gauge)
    - `batch.step.write.count` — количество записанных записей (Gauge)
    - `batch.step.skip.count` — количество пропущенных записей (Gauge)
    - `batch.step.started/completed` — счётчики запусков (Counter)

5. **Готовность к Grafana.** Prometheus — нативный data source для Grafana. Все метрики сразу доступны для построения дашбордов через PromQL.

### Отклонённые альтернативы

- **JMX Exporter:** требует включения JMX в JVM (дополнительный overhead), менее гранулярный контроль над метриками, сложнее добавлять кастомные метрики.
- **Telegraf:** добавляет дополнительный контейнер в под, усложняет архитектуру без значительных преимуществ для Spring Boot.
- **OpenTelemetry:** избыточен для текущих задач (нужен в первую очередь для распределённой трассировки), более сложный SDK.

## 3. Конфигурация оповещений (Alerting)

### Выбор системы оповещений: Grafana Alerting

**Обоснование выбора Grafana вместо Prometheus AlertManager:**

1. **Единый интерфейс.** Команда уже использует Grafana для дашбордов — оповещения настраиваются в том же UI, не нужно переключаться между системами.

2. **Визуальное создание правил.** Grafana позволяет создавать алерты прямо из графиков: увидели аномалию → выделили область → создали алерт. Это снижает порог входа для команды без опыта PromQL.

3. **Множество каналов уведомлений.** Grafana из коробки поддерживает email, Slack, Telegram, PagerDuty, Webhook — можно гибко настроить эскалацию.

4. **Шаблонизация сообщений.** Можно включить в уведомление график, значения метрик, ссылку на дашборд — ускоряет реакцию на инцидент.

## 4. Архитектура решения## 4. Архитектура решения

### Обоснование архитектуры:

1. **Разделение потоков логов и метрик.** Логи идут через Filebeat (push-модель), метрики забираются Prometheus (pull-модель). Это стандартный паттерн, позволяющий оптимизировать каждый поток под свои задачи: логи требуют индексации и полнотекстового поиска, метрики — быстрого временного ряда.

2. **Filebeat на хосте, а не в контейнере приложения.** Filebeat монтирует том с логами как read-only, не влияя на работу приложения. При перезапуске приложения логи не теряются.

3. **Logstash для трансформации.** Хотя Filebeat может отправлять прямо в Elasticsearch, Logstash даёт возможность:
    - Парсить и нормализовать JSON-логи
    - Добавлять метаданные (окружение, версия приложения)
    - Буферизировать события при пиковых нагрузках
    - Перенаправлять в несколько систем (например, в архив S3 для аудита)

4. **Prometheus pull-модель.** Приложение не должно заботиться о доставке метрик — оно просто expose'ит endpoint. Prometheus сам скрейпит его с заданным интервалом. Это упрощает приложение и гарантирует, что метрики не потеряются при сетевых сбоях (Prometheus повторит скрейп).

## 6. Заключение

Выбранный стек (Micrometer + Prometheus + Grafana для метрик, Filebeat + Logstash + Elasticsearch + Kibana для логов) обеспечивает:

- ✅ Соответствие всем нефункциональным требованиям (мониторинг, алертинг, централизованные логи)
- ✅ Нативную интеграцию со Spring Boot и Spring Batch
- ✅ Минимальные изменения в коде приложения
- ✅ Возможность масштабирования при росте бизнеса
- ✅ Готовность к миграции в облачную инфраструктуру GCP
