# Обоснование выбора метрик

## Что мониторим и почему

Метрики выбраны так, чтобы покрыть три вопроса, которые возникают у команды TradeWare при инциденте:
**«живо ли приложение» → «хватает ли ему ресурсов» → «выполнилась ли бизнес-задача»**.

### Уровень 1. Доступность

| Метрика | Источник | Зачем |
|---|---|---|
| `up{job="batch-processing"}` | Prometheus target | Факт, что приложение отвечает на scrape. Первый индикатор аварии; на нём построен алерт `BatchAppDown` |

### Уровень 2. Ресурсы JVM

ETL обрабатывает отчёты до 400 тыс. строк в сутки (в пике ×2–3), поэтому давление на память и GC — главные технические риски.

| Метрика | Источник | Зачем |
|---|---|---|
| `process_cpu_usage` | Micrometer/JVM | Перегрузка CPU при параллельных загрузках |
| `jvm_memory_used_bytes{area="heap"}` / `jvm_memory_max_bytes` | Micrometer/JVM | Рост heap → риск OOM на больших файлах; алерт `HighHeapUsage` при >85% |
| `jvm_threads_live_threads` | Micrometer/JVM | Утечки потоков, проблемы пула |
| `jvm_gc_pause_seconds` | Micrometer/JVM | Длинные GC-паузы напрямую удлиняют время обработки отчёта (SLA — 30 с на 2000 строк) |
| `http_server_requests_seconds` | Micrometer | Отклик actuator-эндпоинтов — косвенный признак деградации |

### Уровень 3. Бизнес-метрики ETL (кастомные, добавлены в `JobCompletionNotificationListener`)

| Метрика | Тип | Зачем |
|---|---|---|
| `etl_job_runs_total{job,status}` | Counter | Сколько запусков и с каким статусом завершились; алерт `EtlJobFailed` реагирует на `status="FAILED"` |
| `etl_records_read_total{step}` | Counter | Сколько строк отчёта прочитано — контроль полноты загрузки |
| `etl_records_written_total{step}` | Counter | Сколько строк попало в `products`; расхождение с read без skip = проблема |
| `etl_records_skipped_total{step}` | Counter | Сколько битых строк пропущено — индикатор качества входных данных от складов |
| `etl_job_duration_seconds` | Timer | Длительность джобы — прямой контроль SLA «2000 строк ≤ 30 секунд» |

Именно кастомные метрики (а не только JVM) закрывают исходную боль кейса: «отчёты висят, обновления не применяются» — теперь это видно количественно.

## Способ доставки метрик: Actuator + Micrometer → `/actuator/prometheus` ← Prometheus scrape

Задание допускало Prometheus Agent или JMX Exporter. Выбран нативный для Spring Boot путь (pull-модель Prometheus):

| Критерий | Actuator + Micrometer | JMX Exporter |
|---|---|---|
| Подключение | 2 зависимости + 2 строки конфигурации | Java-agent, YAML-маппинг MBeans |
| Кастомные метрики | `MeterRegistry` прямо в коде слушателя джобы | Ручная регистрация MBean — для бизнес-метрик неудобно |
| Метрики Spring Batch/JVM | Автоматически | Только то, что замаплено вручную |
| Эксплуатация | Нет дополнительных процессов | Отдельный агент в каждом JVM-процессе |

JMX Exporter оправдан для легаси-приложений без возможности менять код (например, существующего монолита на WildFly) — для нового Spring Boot-сервиса Actuator проще и богаче.

В продакшене на GCP та же схема работает через Google Managed Service for Prometheus (scrape того же эндпоинта) без изменения приложения.
