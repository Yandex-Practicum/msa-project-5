# Обоснование выбора способа отправки логов и конфигурации оповещений

## Выбор способа отправки логов
* Решение: filebeat -> logstash -> elasticsearch.
* Логи spring batch отправляются из приложения через filebeat, который собирает файлы /app/logs/app.log, передает их в logstash для парсинга и индексирует в Elasticsearch. Kibana используется для визуализации.
* Обоснование: стек ELK обеспечивает централизованное хранение и поиск логов, что важно для монитринга расрпделенных систем. Logstash позволяет преобразовать логи в json добавляя поля-MDC, что позволит упростить корреляцию с трейсингом Jaeger. Также ELK стем поддерживает горизонтальное масштабирование.
* Из альтернатив рассматривался прямой экспорт логов через logback в elasticsearch, но это менее гибко для сложный парсингов.

### Конфигурация
* Логи пишутся в файл /app/logs/app.log
* Filebeat настроен на мониторинг этого файла с отправкой в logstash
* Logstash парсит логи и индексирует в Elasticsearch с индексом app-logs-{date}

## Выбор способа оповещений
* Решение: оповещение через prometheus с использованием alertmanager
* Prometheus собирает метрики через встроенный эндпоинт Actuator, оповещения настраиваются через файл alerting_rules.yml и отрпавляются через alertmanager
* Обоснование: интеграция с метриками (micrometer) обеспечивает встроенный экспорт метрик без необходимости дополнительного jmx exporter. Prometheus alertmanager позводяет задавать сложные условия и маршрутизацию уведомлений на разные каналы.
* Из альтернатив рассматривалась настройка алертов через grafana, но использование alertmanager предпочтительнее для центраизованного управления правилами и обеспечения отказоустойчивости.

### Конфигурация алертов
* Первый алерт: `histogram_quantile(0.95, sum(rate(batch_job_duration_seconds_bucket{job_name="importProductJob", status="COMPLETED"}[5m])) by (le)) > 30` - алерт при превышении 95-го перцентиля длительности Job importProductJob более 30 секунд за последние 5 минут
* Второй алерт: `increase(loyalty_updates_failed_total{job="batch-processing"}[1h]) > 5` - алерт при увеличении счётчика неудачных обновлений лояльности более чем на 5 за последний час
* Третий алерт: `clamp_max(jvm_memory_used_bytes{area="heap", id="G1 Old Gen", job="batch-processing"} / jvm_memory_max_bytes{area="heap", id="G1 Old Gen", job="batch-processing"} * 100, 100) > 90` - алерт при использовании более 90% кучи JVM за последние 5 минут
