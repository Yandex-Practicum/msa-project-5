# Трассировка запуска Spring Batch

## Выбор

Micrometer Tracing с Brave интегрируется с Spring Boot и использует серверную HTTP-observation. Она создаёт или продолжает контекст запроса, а интеграция с журналом добавляет `traceId` и `spanId` в MDC. W3C Trace Context выбран как стандартный формат входящего заголовка `traceparent`. Для локальной демонстрации выборка установлена в 100%; экспорт span в отдельную систему трассировки не настроен.

Фильтр добавляет в MDC URI без строки запроса и очищает его после завершения обработки. JSON-лог содержит эти поля наряду с временем, уровнем, именем сервиса, сообщением и при необходимости стеком ошибки. Logback → Filebeat → Logstash → Elasticsearch → Kibana даёт единый поиск событий по `traceId`. В логах не записываются CSV, тела запросов или query-параметры.

Альтернатива — вручную генерировать и прокидывать случайный идентификатор в заголовке и MDC. Она проще для одного сервиса, но не обеспечивает стандартную модель span и совместимость с распределённой трассировкой. OpenTelemetry SDK/collector удобен для полноценного экспорта и анализа трасс, но для задачи поиска коррелированных логов дополнительные компоненты не обязательны.

## Сценарий

1. Клиент вызывает `POST /jobs/import`; при наличии корректного `traceparent` сервер продолжает существующую трассу, иначе создаёт новую.
2. Контроллер пишет событие и запускает Batch через явно настроенный синхронный исполнитель.
3. События Batch выполняются в контексте того же HTTP-потока и содержат идентификаторы и URI. Наблюдение Spring Batch может создавать вложенные span: `traceId` остаётся общим, а `spanId` отдельных событий отличается.
4. API возвращает `executionId`, итоговый статус и `traceId`; пользователь ищет логи по нему в Kibana.

В процессе ошибки API не должен выдавать стек или внутренние данные клиенту; подробности фиксируются в журнале. Если запрос не достиг обработчика или оборвался раньше создания контекста, `traceId` в ответе может отсутствовать. Трассировка не гарантирует доставку каждого события при сбоях стека логирования.

## Ограничения

Ожидание ответа и тайм-ауты делают подход неудобным для больших файлов и интенсивной нагрузки. Для целевой системы следует рассмотреть очередь и асинхронную обработку; при этом понадобится перенос контекста в фоновые потоки/сообщения, корреляция по `executionId` и повторная проверка ошибок и доставки. Для промышленной эксплуатации необходимы TLS, контроль доступа, безопасное хранение и маскирование логов, политики хранения и защищённый сбор событий.
