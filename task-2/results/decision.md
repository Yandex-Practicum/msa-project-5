# Обоснование выбора технологического решения

## Сравнительный анализ технологий

| Критерий | Spring Batch | Apache Airflow | K8s Job | Spark |
|----------|--------------|----------------|---------|-------|
| **Наличие конфигурации CRON-расписания** | ⚠️ Частично: `@Scheduled` держит JVM запущенной круглые сутки, иначе нужен внешний триггер | ✅ Полноценно: расписание — декларативное свойство DAG, встроенный scheduler | ✅ Полноценно: нативный ресурс CronJob с cron-выражением | ❌ Отсутствует: нужен внешний планировщик |
| **Сложность реализации логики по обработке данных** | ⚠️ Средняя: каркас Job/Step/Reader/Writer избыточен для одного SQL JOIN и записи файла | ⚠️ Низкая сама по себе (один Python-файл DAG), но ценой внедрения целой платформы | ✅ Низкая: простой скрипт (~100–150 строк), упакованный в контейнер | ❌ Высокая: поднятие сессии, драйвер/executor ради тривиального JOIN |
| **Ресурсоёмкость решения** | ⚠️ Низкая на выгрузку, но JVM (~256–512 МБ) даже для простого экспорта; с `@Scheduled` — круглосуточно | ❌ Средняя/высокая: постоянные scheduler + webserver + metadata DB (~0,5–1 ГБ) 24/7 ради 10–15 минут работы в сутки | ✅ Минимальная: под на 10–15 минут в сутки (~128–256 МБ), ничего постоянного | ❌ Высокая: кластер/драйвер от 1–2 ГБ даже в минимальной конфигурации |
| **Масштабируемость решения под нагрузкой и сложность реализации** | ⚠️ Средняя: партиционирование и remote chunking требуют заметной настройки | ✅ Высокая: параллелизм задач из коробки — но избыточная для одного ежедневного запуска | ✅ Достаточная: рост объёмов закрывается ресурсами пода или сегментированными Job-ами | ✅ Очень высокая: горизонтальная по кластеру, но не востребована при 10 тыс. строк |
| **Сложность развёртывания в облаке и интеграция с микросервисной архитектурой** | ✅ Низкая: стандартный Docker-образ и пайплайн | ❌ Средняя/высокая: отдельный Helm-чарт, metadata DB, обновления, бэкапы — новый компонент для эксплуатации | ✅ Минимальная: один манифест CronJob в существующем кластере, те же Secrets и CI/CD | ❌ Высокая: отдельный Spark-кластер или operator, новая инфраструктура |
| **Удобство интеграции с системами логирования и мониторинга** | ✅ Хорошее: Actuator + Micrometer → Prometheus, логи в stdout | ✅ Отличное: UI с логами и историей — но это вторая консоль рядом с уже имеющимися Grafana/ELK | ⚠️ Базовое, но достаточное: метрики CronJob через kube-state-metrics → Prometheus, логи пода → общий стек кластера | ⚠️ Хорошее: Spark UI и метрики, но ещё одна консоль для эксплуатации |

## Выбранное решение: Kubernetes CronJob (скрипт-экспортер в контейнере)

## Обоснование выбора

### 1. Простота задачи соответствует простоте решения

Задача — один SQL JOIN без бизнес-логики, 5 000–10 000 строк, один запуск в сутки. Всё, что сверх простого скрипта, — каркас ради каркаса: Spring Batch требует описать Job/Step/Reader/Writer и поднять JVM там, где достаточно одного запроса со стримингом результата; Airflow и Spark тем более избыточны. Тот же вывод делают авторы курса в Задании 3 — для объёмов в 100 раз больших (до 1 млн строк) выбран простой экспорт через k8s CronJob.

### 2. Минимальное потребление ресурсов

Под живёт только во время выгрузки (~128–256 МБ на 10–15 минут в сутки). Всё остальное время ресурсы кластера свободны — никаких постоянно работающих компонентов, в отличие от Airflow (scheduler + webserver + metadata DB 24/7) и варианта «Spring Batch с @Scheduled».

### 3. Эксплуатационные сценарии закрыты нативно

CronJob из коробки даёт расписание (`schedule: "0 6 * * *"`), ретраи (`backoffLimit`), гарантию старта (`startingDeadlineSeconds`), защиту от параллельных запусков (`concurrencyPolicy: Forbid`) и историю запусков (`successfulJobsHistoryLimit` / `failedJobsHistoryLimit`). Ручной перезапуск за произвольную дату — одна команда `kubectl create job --from=cronjob/price-list-export`.

### 4. Нативная интеграция с текущей архитектурой

CronJob — часть Kubernetes API: тот же кластер, что у остальных микросервисов, те же Secrets для подключения к БД, тот же CI/CD-пайплайн, тот же стек наблюдаемости. Метрики запусков собираются через kube-state-metrics в Prometheus/Grafana, логи пода уходят в общий стек логирования — никакой дополнительной инфраструктуры.

### 5. Цена решения осознана

Нет готового UI и развёрнутой истории запусков — для одного ежедневного запуска это закрывается логами, метриками и алертом «нет успешного запуска к 06:30». Если со временем появятся десятки пакетных сценариев с зависимостями и ветвлениями — миграция на Airflow не потребует переписывания скрипта (`KubernetesPodOperator` запустит тот же контейнер). Заранее платить за платформу «на вырост» — преждевременно.

## Как работает решение

1. CronJob `price-list-export` по расписанию `0 6 * * *` создаёт Job, и Kubernetes поднимает под со скриптом-экспортером.
2. Скрипт подключается к PostgreSQL (креды из Kubernetes Secret) и выполняет один SELECT с JOIN таблиц products, categories, clients, client_prices, читая результат курсором чанками, чтобы не держать выгрузку в памяти.
3. Строки группируются по клиенту, формируются персональные CSV (при необходимости XLS) на каждого B2B-клиента.
4. Файлы загружаются в объектное хранилище по путям `/price-lists/{client_id}/{yyyy-MM-dd}.csv` — идемпотентно, файл за дату перезаписывается целиком; клиенты забирают прайс-листы по HTTPS.
5. Скрипт пишет структурированные JSON-логи (число строк и файлов), отправляет уведомление об успехе и завершается с exit code 0; при ошибке — exit code 1.
6. При падении пода Kubernetes выполняет повтор (`backoffLimit: 2`); после исчерпания попыток Alertmanager шлёт алерт дата-инженеру, который перезапускает выгрузку вручную.
7. Метрики Job-ов (`kube_job_status_succeeded`, `kube_job_status_failed`, длительность) собираются в Prometheus и отображаются в Grafana; логи доступны в общем стеке логирования кластера.

## Почему не другие решения

- **Apache Airflow** — избыточен: постоянно работающий кластер (scheduler + webserver + metadata DB) ради одного ежедневного задания без ветвлений и зависимостей — неоправданные ресурсы и сложность эксплуатации.
- **Spring Batch** — избыточен для простого SQL-экспорта: JVM, Spring-конфигурация, описание Job/Step/Reader/Writer там, где достаточно одного скрипта. Оправдан при сложной логике обработки, которой здесь нет по условию задачи.
- **Spark** — избыточен на порядки: распределённый движок для 10 тыс. строк, отдельный кластер и нет CRON из коробки.

## Вывод

**Kubernetes CronJob с простым скриптом-экспортером** — решение, соразмерное задаче: расписание, ретраи и изоляция запусков предоставляются Kubernetes, наблюдаемость — имеющимся стеком мониторинга, а ресурсы потребляются только на время выгрузки. Решение не требует ни дополнительной инфраструктуры (Airflow, Spark), ни фреймворков (Spring Batch) и органично вписывается в существующую микросервисную архитектуру магазина.
