# План имплементации и конфигурации решения

## Пошаговый план имплементации

### Шаг 1: Подготовка окружения (1 день)

- Создать Git репозиторий
- Настроить CI/CD пайплайн (GitLab CI/GitHub Actions)
- Подготовить Docker registry для образов

### Шаг 2: Разработка Spring Boot приложения (2-3 дня)

- Инициализировать проект через Spring Initializr
- Добавить зависимости: Spring Batch, PostgreSQL, AWS SDK, Spring Mail
- Реализовать модели данных
- Настроить DataSource для подключения к PostgreSQL
- Создать SQL-запрос с JOIN'ами для получения данных

### Шаг 3: Реализация Spring Batch Job (2 дня)

- Создать ItemReader с оптимизированным SQL-запросом
- Реализовать ItemProcessor для форматирования данных
- Создать FlatFileItemWriter для генерации CSV
- Реализовать S3 uploader
- Настроить композитный Writer

### Шаг 4: Настройка мониторинга и уведомлений (1 день)

- Подключить Spring Actuator и Micrometer
- Настроить экспорт метрик в Prometheus
- Реализовать JobExecutionListener для отправки email
- Настроить логирование в ELK стек

### Шаг 5: Контейнеризация (0.5 дня)

- Написать Dockerfile с multi-stage сборкой
- Оптимизировать размер образа
- Настроить healthcheck'и

### Шаг 6: Kubernetes манифесты (1 день)

- Создать CronJob манифест
- Настроить ConfigMap и Secret
- Создать ServiceAccount и RBAC
- Настроить Resource Quotas

### Шаг 7: Тестирование (1-2 дня)

- Unit-тесты для компонентов Spring Batch
- Интеграционные тесты с TestContainers
- Тестирование в staging окружении
- Нагрузочное тестирование

### Шаг 8: Деплой и мониторинг (0.5 дня)

- Применить Kubernetes манифесты
- Настроить алерты в Prometheus/Grafana
- Создать дашборды для мониторинга
- Документировать процесс

## Ключевые метрики мониторинга

Метрики Prometheus:
  - price_list_generation_duration_seconds      # время выполнения
  - price_list_records_processed_total          # количество обработанных записей
  - price_list_file_size_bytes                  # размер сгенерированного файла
  - price_list_errors_total                     # количество ошибок
  - spring_batch_job_status                     # статус выполнения Job

Алерты:
  - Job не запустился в течение 5 минут после запланированного времени
  - Время выполнения превысило 10 минут
  - Job завершился с ошибкой
  - Размер файла меньше 100KB (возможно, проблема с данными)

## Преимущества выбранного решения

### 1. Минимальные затраты ресурсов

| Преимущество | Описание |
|--------------|----------|
| **Pod работает только во время выполнения Job** | В отличие от постоянно запущенных сервисов (как Airflow), контейнер существует только в момент генерации прайс-листа (2-3 минуты в день). Всё остальное время ресурсы кластера свободны для других задач. |
| **Выделяется 256-512 MB RAM** | Этого объёма памяти достаточно для обработки 5 000–10 000 строк данных с использованием потокового чтения (`JdbcCursorItemReader`), которое не загружает весь набор данных в память. |
| **Нет постоянно работающих сервисов** | В отличие от Airflow, который требует постоянной работы веб-сервера, планировщика, очереди сообщений (Redis/RabbitMQ) и базы данных, решение на CronJob не потребляет ресурсы в режиме ожидания. |

### 2. Простота эксплуатации

| Преимущество | Описание |
|--------------|----------|
| **Стандартный Spring Boot стек, знакомый команде** | Используется Java 17 + Spring Boot + Spring Batch — технологии, на которых уже построены остальные микросервисы магазина. Команде не требуется изучать Python/Airflow или Scala/Spark. Единый кодстайл, общие библиотеки, одинаковые подходы к тестированию. |
| **Нативная интеграция с K8s экосистемой** | CronJob — нативный ресурс Kubernetes. Не требуется установка операторов или сторонних контроллеров. Управление через стандартный `kubectl` или GitOps (ArgoCD/Flux). |
| **Автоматические ретраи при сбоях** | `backoffLimit: 2` в спецификации CronJob гарантирует до двух повторных попыток при падении Pod'а. Дополнительно Spring Batch предоставляет встроенные механизмы retry/skip на уровне ItemReader и ItemProcessor. |

### 3. Надёжность

| Преимущество | Описание |
|--------------|----------|
| **K8s гарантирует запуск по расписанию** | Kubernetes Scheduler отслеживает CronJob и гарантирует запуск ровно в 6:00 (с учётом `startingDeadlineSeconds`). При пропуске запуска (например, простой кластера) генерируется событие, которое можно отследить через алерты. |
| **Встроенные механизмы повторных попыток** | Два уровня ретраев: инфраструктурный (K8s перезапускает упавший Pod) и прикладной (Spring Batch повторяет неудачные chunk'и). Это защищает как от временных сетевых сбоев, так и от ошибок валидации отдельных записей. |
| **Полная изоляция выполнения** | Каждый запуск происходит в отдельном Pod'е с собственными ресурсами (CPU, память, диск). Ошибка в одном запуске не влияет на последующие. `concurrencyPolicy: Forbid` исключает параллельные выполнения и гонки данных. |

### 4. Мониторинг и наблюдаемость

| Преимущество | Описание |
|--------------|----------|
| **Метрики Prometheus из коробки** | Spring Actuator + Micrometer автоматически экспортируют метрики JVM (память, потоки, GC) и бизнес-метрики (длительность выполнения, количество записей, размер файла). Prometheus собирает их по аннотациям Pod'а без дополнительной настройки. |
| **Централизованное логирование через ELK** | Логи приложения пишутся в stdout/stderr и автоматически собираются Fluentd/Filebeat в Elasticsearch. Kibana позволяет искать ошибки по тегам, времени и ключевым словам. Структурированное логирование (JSON) упрощает парсинг. |
| **Автоматические уведомления о статусе** | `JobExecutionListener` отправляет email со статистикой после каждого выполнения: количество обработанных записей, размер файла, длительность. При ошибке уведомление содержит стектрейс и ссылку на логи в Kibana. |

## Вывод

**Kubernetes CronJob + Spring Boot (Spring Batch)** — оптимальное решение, которое:

- ✅ Обеспечивает **надёжную генерацию прайс-листов каждое утро в 6:00**
- ✅ Потребляет **минимальные ресурсы** (Pod запущен всего 2-3 минуты в день)
- ✅ **Легко интегрируется** в существующую микросервисную архитектуру онлайн-магазина
- ✅ Не требует **дополнительной инфраструктуры** (в отличие от Airflow/Spark)
- ✅ Предоставляет **полную наблюдаемость** через стандартные средства мониторинга

Решение соответствует всем функциональным и нефункциональным требованиям задачи и готово к внедрению в production-среду.
