# Разработка дизайна модуля пакетной обработки данных

Сценарий: каждое утро в 6:00 нужно сгенерировать CSV/XLS прайс-листы для B2B-клиентов на основе данных из `products`, `categories`, `clients`, `client_prices` (5 000–20 000 строк суммарно). Дополнительной логики обработки не требуется — только связать таблицы и выгрузить результат. Инфраструктура — микросервисы в k8s.

## 1. Обоснование выбора технологического решения

| Критерий | Spring Batch | Apache Airflow | K8s Job (CronJob) | Spark |
|---|---|---|---|---|
| Наличие конфигурации CRON-расписания | Нет своего - нужен внешний триггер (Quartz, Spring Cloud Task Scheduler или k8s CronJob) | Есть нативно - `schedule` в определении DAG | Есть нативно - CronJob (`schedule: "0 6 * * *"`) | Нет - только через `spark-submit`, запускаемый извне |
| Сложность реализации логики по обработке данных | Модель Job/Step/ItemReader/ItemWriter избыточна для простого join+экспорта без доп. логики | Один SQL/Python-оператор с запросом - несложно, но пайплайн ради одного шага не нужен | Минимальна - один скрипт (подключение к БД, запрос, запись CSV) | DataFrame API и Spark-сессия избыточны для 5–20 тыс. строк - такой объём не требует распределённой обработки |
| Ресурсоёмкость решения | Средняя - JVM-процесс на время выполнения джоба | Высокая - постоянно работающие webserver, scheduler и БД метаданных ради пары минут работы в сутки | Минимальная - под поднимается только в 6:00 и гаснет после завершения | Высокая - драйвер и экзекьюторы, ощутимо тяжелее, чем требует такой объём данных |
| Масштабируемость под нагрузкой и сложность реализации | Поддерживает partitioning/parallel steps, но это дополнительная конфигурация, не нужная при текущем объёме | Сам не обрабатывает данные - масштабируется как оркестратор, а не как обработчик, что здесь не требуется | Растёт вертикально (больше CPU/памяти поду) - для десятков тысяч строк достаточно | Лучше всех масштабируется на большие объёмы, но эта возможность здесь не нужна |
| Сложность развёртывания в облаке и интеграция с микросервисной архитектурой | Контейнеризуется легко, но нужен внешний планировщик поверх - ещё одна часть в сборке | Отдельная платформа для развёртывания и поддержки (БД, scheduler, webserver) - новый тяжёлый компонент ради одной задачи | Ложится нативно: тот же кластер, тот же CI/CD, тот же реестр образов, что и у остальных микросервисов | Нужен Spark-кластер (standalone или k8s-operator) - новый тяжёлый компонент, несоразмерный задаче |
| Удобство интеграции с системами логирования и мониторинга | Хорошее - Spring Boot Actuator/Micrometer, стандартное логирование | Лучшее из всех - встроенный UI истории запусков, Grid/Gantt, StatsD-экспортёр | Логи - через stdout/stderr в тот же стек, что и у остальных микросервисов; история запусков и метрики не встроены, настраиваются отдельно | Свой UI/history server, интеграция с Prometheus - тоже отдельная система ради одной задачи |

**Вывод.** K8s CronJob — единственный вариант, где все шесть характеристик соразмерны самой задаче: простой ежедневный join+экспорт небольшого объёма в уже готовой k8s-инфраструктуре. Spring Batch и Spark не имеют своего расписания и всё равно потребовали бы CronJob сверху; Airflow и Spark добавляют несоразмерно тяжёлую инфраструктуру ради задачи, которая для этого недостаточно сложна. Единственный минус K8s CronJob — слабая наблюдаемость из коробки (нет истории запусков и UI, как у Airflow), но решается логированием и мониторингом, которые уже используется остальными микросервисами.

Как решение работает: K8s CronJob `pricelist-generator` запускается по расписанию `0 6 * * *` (каждое утро в 6:00). Под подключается к той же БД PostgreSQL, где лежат `products`, `categories`, `clients`, `client_prices`, выполняет JOIN-запрос по этим таблицам, формирует CSV/XLS и записывает результат в объектное хранилище (S3/GCS-совместимое) — оттуда прайс-листы становятся доступны B2B-клиентам. После завершения под гаснет до следующего запуска. Никакого постоянно работающего сервиса не появляется — только ещё один под по образцу уже существующих в кластере.

## 2. Верхнеуровневый план внедрения

### Имплементация

1. Написать скрипт/приложение генерации прайс-листа (на удобном языке): подключение к Postgres → SQL-запрос с JOIN по таблицам → формирование CSV → запись результата в объектное хранилище.
2. Обернуть в Docker-образ и добавить в существующий CI/CD и реестр образов.

### Конфигурация

3. Настроить доступ пода к БД: Secret с кредами, ServiceAccount с минимально необходимыми правами.
4. Настроить доступ пода к объектному хранилищу: Secret/IAM-роль на запись файлов.
5. Написать манифест `CronJob`: `schedule: "0 6 * * *"`, нужный `image`, `resources.requests/limits`, `restartPolicy: OnFailure`, `concurrencyPolicy: Forbid` (чтобы не запускались параллельные прогоны, если предыдущий не успел завершиться).
6. Логи — вывод в stdout/stderr, чтобы существующий агент сбора логов подхватывал их так же, как у остальных сервисов.
7. Базовый алерт на неуспешный Job — через kube-state-metrics + Prometheus (метрика `kube_job_status_failed`), чтобы узнать о сбое раньше, чем это заметит B2B-клиент при отсутствии свежего прайс-листа.

### Проверка

8. Тестовый прогон вручную (`kubectl create job --from=cronjob/pricelist-generator manual-test`), проверить корректность файла и логи.
9. Задеплоить в целевой namespace, дождаться первого планового запуска в 6:00, проверить результат.
