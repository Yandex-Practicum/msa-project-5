# Выбор оркестратора пакетной обработки

Для сценария маркетинга выбран Apache Airflow. Он управляет зависимостями шагов, ветвлением и повторными попытками, а сами тяжёлые вычисления можно выносить в Spark или облачные задания. Один миллион записей за запуск не следует передавать между задачами через XCom: данные остаются в хранилище, задачи передают ссылки и контрольные значения.

| Требование | Реализация в Airflow |
|---|---|
| BigQuery | Готовые операторы и хуки провайдера Google для запросов и загрузки данных |
| Redshift | Готовые SQL-операторы и AWS-провайдер; загрузка через S3 и Redshift COPY |
| Kafka | Провайдер Apache Kafka с операторами и сенсорами; для массовых потоков сохранять события вне XCom |
| Spark | Провайдер Apache Spark и SparkSubmitOperator для запуска распределённой обработки |
| Внешние API | HTTP-провайдер или Python-задача с HTTP-клиентом |
| Условия и ветвление | BranchPythonOperator, правила запуска и условные задачи |
| Событийный запуск | REST API, внешние триггеры и сенсоры; для событийных источников возможен запуск DAG по API |
| Fallback | Отдельная ветвь или задача с подходящим trigger rule; готового универсального fallback для любой бизнес-ошибки нет |
| Retry | Настройки retries и retry_delay на уровне задачи |
| Email | EmailOperator и SMTP; нужен настроенный почтовый сервер |
| Мониторинг | Интерфейс DAG и задач, журналы, метрики и уведомления |

В облаке Airflow можно разместить в управляемом сервисе или на Kubernetes. Для рабочей нагрузки потребуются внешние БД метаданных, удалённое хранилище логов, секреты для подключений и масштабируемые исполнители.
