# Обоснование выбора Apache Airflow для обработки данных маркетингового отдела

## 1. Выбор технологического решения

В качестве технологического решения для пакетной обработки данных выбран **Apache Airflow 2.7.3**.

### Обоснование выбора:

**Apache Airflow** — это платформа для создания, планирования и мониторинга рабочих процессов с открытым исходным кодом. Написана на Python, что делает её гибкой и расширяемой. Airflow позволяет создавать сложные пайплайны обработки данных как код (DAG — Directed Acyclic Graph).

**Ключевые преимущества для нашей задачи:**

- **Гибкость**: пайплайны описываются кодом на Python, что позволяет реализовать любую логику обработки
- **Масштабируемость**: способен обрабатывать 1M+ записей за запуск благодаря распределённой архитектуре
- **Расширяемость**: сотни готовых провайдеров для интеграции с различными системами
- **Мониторинг**: встроенный веб-интерфейс для отслеживания выполнения задач
- **Надёжность**: встроенные механизмы retry, fallback и оповещений
- **Сообщество**: одно из крупнейших open-source сообществ, регулярные обновления

**Сравнение с альтернативами:**

| Критерий | Apache Airflow | Prefect | Dagster | Jenkins |
|----------|---------------|---------|---------|---------|
| Интеграция с BigQuery/Redshift | ✅ Встроенные операторы | ✅ Через библиотеки | ✅ Через библиотеки | ⚠️ Через скрипты |
| Ветвление пайплайнов | ✅ BranchPythonOperator | ✅ Условные операторы | ✅ Встроенная логика | ❌ Ограничено |
| Event-триггеры | ✅ Sensors/Triggers | ✅ Встроенные | ✅ Встроенные | ⚠️ Плагины |
| Retry/Fallback | ✅ Из коробки | ✅ Из коробки | ✅ Из коробки | ⚠️ Плагины |
| Email-уведомления | ✅ Встроенные | ✅ Через automation | ✅ Через alerts | ✅ Плагины |
| Облачная поддержка | ✅ GCP/AWS/Azure managed | ✅ Cloud/Server | ✅ Cloud/Hybrid | ⚠️ Требует настройки |
| Сложность внедрения | Низкая | Средняя | Средняя | Высокая |

**Вывод**: Apache Airflow — оптимальный выбор для задачи маркетингового отдела благодаря лучшей экосистеме готовых интеграций, зрелости решения и наличию managed-сервисов в облаках.

## 3. Возможности ветвления, условных операторов и event-триггеров

### 3.1. Ветвление (Branching)

Airflow предоставляет `BranchPythonOperator` для динамического ветвления пайплайна.

**Результат:** Пайплайн автоматически выбирает путь выполнения на основе анализа данных. В Graph View наглядно видно, какая ветка выполнилась, а какая пропущена.

---

### 3.2. Условные операторы

**Trigger Rules** — управление запуском задач в зависимости от статуса предыдущих:

| Trigger Rule | Описание |
|--------------|----------|
| `ALL_SUCCESS` | Все предыдущие задачи успешны |
| `ONE_FAILED` | Хотя бы одна задача упала |
| `ALL_DONE` | Все задачи завершены (независимо от статуса) |
| `NONE_FAILED` | Ни одна задача не упала |
| `ONE_SUCCESS` | Хотя бы одна задача успешна |

**Дополнительные механизмы:**

- **ShortCircuitOperator** — остановка всего пайплайна при выполнении условия
- **Jinja Templating** — условная логика в параметрах задач: `{{ execution_date }}`

---

### 3.3. Event-триггеры (Sensors)

**Готовые сенсоры для внешних событий:**

| Сенсор | Назначение |
|--------|------------|
| `ExternalTaskSensor` | Ожидание завершения другого DAG |
| `S3KeySensor` | Ожидание появления файла в S3 |
| `KafkaSensor` | Ожидание сообщения в Kafka-топике |
| `BigQueryTableExistenceSensor` | Ожидание создания таблицы |
| `DateTimeSensor` | Ожидание наступления времени |

---

### Вывод:

Airflow полностью поддерживает все требуемые сценарии: **динамическое ветвление**, **условную логику** через Trigger Rules и **реакцию на внешние события** через встроенные сенсоры.## 3. Возможности ветвления, условных операторов и event-триггеров
