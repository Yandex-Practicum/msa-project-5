# Выбор и реализация решения для пакетной обработки данных

## 1. Обоснование выбора технологического решения

Выбор технологического решения для пакетной обработки данных маркетингового отдела: объединение данных из CSV, PostgreSQL и Kafka, формирование отчётов.

### Требования к решению

| № | Требование |
| :-: | :- |
| 1 | Интеграция с BigQuery, Redshift, Kafka и Spark, желательно готовыми модулями |
| 2 | Поддержка ветвления, условных операторов и event-triggers |
| 3 | Retry, fallback-logic и email-уведомления без написания инфраструктуры с нуля |
| 4 | Встроенный мониторинг и оповещения |
| 5 | Объём данных за один запуск пайплайна — около 1 млн строк |
| 6 | Локальное развёртывание с возможностью последующего переноса в облачную инфраструктуру |

### Решение

**Выбранный вариант: Apache Airflow.**

Airflow — оркестратор пайплайнов, описывающий пайплайн как DAG (граф задач в Python-коде). Для всех четырёх целевых систем есть официальные provider-пакеты: `apache-airflow-providers-google` (BigQuery: `BigQueryInsertJobOperator`, `BigQueryToGCSOperator`), `apache-airflow-providers-amazon` (Redshift: `RedshiftDataOperator`, `RedshiftSQLOperator`, `RedshiftToS3Operator`), `apache-airflow-providers-apache-kafka` (продюсер/консьюмер операторы и сенсоры на топики), `apache-airflow-providers-apache-spark` (`SparkSubmitOperator`, `SparkJDBCOperator`). Это устанавливаемые pip-пакеты — интеграцию не нужно писать с нуля.

Ветвление реализуется через `BranchPythonOperator` (или `@task.branch`): по результату колбэка пайплайн идёт по одной из веток, остальные помечаются `skipped`. Событийные запуски — через сенсоры (`FileSensor`, `S3KeySensor`, `ExternalTaskSensor`) и датасет-ориентированное планирование (Airflow Datasets), которые запускают DAG по появлению данных, а не только по расписанию.

Retry (`retries`, `retry_delay`, `retry_exponential_backoff`) задаётся прямо на операторе или в `default_args`. `EmailOperator` (`airflow.operators.email`) отправляет письма через сконфигурированный SMTP; `on_success_callback`/`on_failure_callback` и `trigger_rule` дают произвольную fallback-логику на уровне графа задач. Мониторинг — встроенный веб-интерфейс (Grid/Graph/Gantt по каждому DAG-run) плюс StatsD-экспортёр метрик в Prometheus/Grafana.

Локально Airflow разворачивается через Docker Compose, в облаке — без переписывания DAG-кода: управляемые сервисы (Google Cloud Composer, Amazon MWAA) либо самостоятельный деплой через официальный Helm-чарт на любом Kubernetes (GKE/EKS/AKS), с масштабированием воркеров под нагрузку и тем же хранилищем DAG-файлов (GCS/S3/бакет).

Из рассмотренных вариантов Airflow — единственный закрывает все требования одновременно готовыми средствами: интеграции под все четыре системы, декларативные ветвление/event-triggers/retry/email, и один и тот же DAG-код для локального стенда и облачного деплоя. Сам объём ~1 млн строк за прогон Airflow не обрабатывает напрямую — он оркестрирует шаги, а тяжёлую обработку выполняет целевая система (Spark-джоба, BigQuery-запрос), на которую указывает конкретный оператор.

### Альтернативы

**Альтернатива 1: Dagster.**
Оркестратор с моделью software-defined assets; официальные интеграции `dagster-gcp`, `dagster-aws`, `dagster-pyspark`, `dagster-kafka`.

- Плюсы: ветвление через graph API и событийные `sensors` по возможностям сопоставимы с Airflow; retry настраивается декларативно (`RetryPolicy` на `@op`).
- Минусы: библиотека провайдеров моложе и меньше, чем у Airflow — под нетиповую операцию выше шанс, что готового оператора нет; email-уведомления не входят во фреймворк, их собирают поверх Slack/PagerDuty или пишут кастомный sensor.

**Альтернатива 2: Prefect.**
Pythonic-оркестратор, пайплайн описывается декораторами `@flow`/`@task`; интеграции `prefect-gcp`, `prefect-aws`, Spark — через Databricks-блок, Kafka — через community-блок.

- Плюсы: retry задаётся прямо в декораторе (`@task(retries=..., retry_delay_seconds=...)`); гибкая Python-логика ветвления.
- Минусы: ветвление — обычный `if/else` в коде, а не отдельный оператор с автоматическим `skip`, из-за чего большой разветвлённый граф сложнее читать; email-уведомления не входят в open-source ядро — доступны в платном Prefect Cloud либо пишутся вручную.

**Альтернатива 3: AWS Step Functions.**
Managed-сервис оркестрации на основе state-машин (Amazon States Language).

- Плюсы: Choice-состояния и EventBridge для ветвления/событий, Retry и Catch описываются декларативно прямо в определении стейт-машины.
- Минусы: работает только с сервисами AWS (Redshift — через Redshift Data API, Spark — через EMR/Glue); под BigQuery готовой интеграции нет. Существует только как облачный сервис — полноценно поднять его локально нельзя (LocalStack эмулирует лишь часть возможностей). Email — только через SNS-подписку, ещё один сервис.

**Альтернатива 4: Apache NiFi.**
GUI-инструмент для потоковой маршрутизации данных, пайплайн собирается визуально из процессоров.

- Плюсы: готовые процессоры под Kafka хорошо проработаны «из коробки»; retry настраивается на уровне процессора, есть готовый процессор `PutEmail`.
- Минусы: под Spark, BigQuery, Redshift готовых процессоров нет — интеграцию пишут через кастомные процессоры/скрипты; сам пайплайн собирается кликами в GUI, а не как код, версионируемый в git.

**Альтернатива 5: Spring Batch + k8s CronJob.**
Java ETL-фреймворк для выполнения шагов джоба, без своего оркестратора — расписание пришлось бы вешать на k8s CronJob.

- Плюсы: retry и skip-policy — сильная сторона самого Spring Batch; `JobExecutionDecider` даёт ветвление внутри джоба.
- Минусы: готовых модулей под BigQuery/Redshift/Kafka/Spark нет — под каждый источник/приёмник пишется свой `ItemReader`/`ItemWriter` вручную; event-triggers не встроены (нужен отдельно Spring Integration/Cloud Stream); email — вручную через `JavaMailSender`; своего планировщика нет вообще, решение собирается из нескольких частей, а не берётся одним продуктом.

### Недостатки, ограничения, риски

1. **Дополнительный сервис для эксплуатации.** Airflow — это своя метабаза (Postgres), scheduler и webserver, которые нужно разворачивать, обновлять и мониторить, как и любой другой компонент инфраструктуры.
2. **XCom не предназначен для больших объёмов данных.** Передавать весь ~1 млн строк между тасками через XCom нельзя — данные должны обрабатываться и передаваться через целевую систему (Spark, BigQuery, файловое хранилище), а через Airflow — только ссылки и метаданные.
3. **LocalExecutor не масштабируется горизонтально.** Для POC его достаточно, но под нагрузку нескольких параллельных пайплайнов и рост объёма потребуется переход на CeleryExecutor или KubernetesExecutor с отдельными воркерами.

## 2. POC-пайплайн

Стек (Docker Compose, `docker-compose.yml`): Postgres (метабаза Airflow), Airflow (LocalExecutor) — webserver + scheduler, MailHog (локальный SMTP-перехватчик, чтобы визуально увидеть отправленные письма без настройки реальной почты).

Источник данных — CSV-файл со статусами доставок (`data/source.csv`).

DAG `batch_processing_demo` (`dags/demo_pipeline.py`):

1. **read_source** — читает CSV.
2. **check_condition** (BranchPythonOperator) — проверяет, есть ли среди прочитанных строк статус `failed`, и в зависимости от результата направляет выполнение в `handle_failures` или в `process_normal`.
3. **handle_failures** — шаг с искусственной нестабильностью (имитирует вызов внешнего сервиса): падает на первых попытках и восстанавливается на третьей; `retries=3`, `retry_delay=10s`.
4. **notify_success** / **notify_failure** (EmailOperator, разные `trigger_rule`) — письмо об успехе финального join-шага или письмо об ошибке, если retry не спасли.

Переменная Airflow `force_fail` (Admin → Variables) позволяет на втором прогоне намеренно исчерпать retry и получить письмо об ошибке — без правки кода между демонстрациями.

## 3. Как запустить

```bash
cd task-1/results
docker compose up -d
```

1. Открыть **http://localhost:8080** (логин/пароль `admin`/`admin`).
2. Включить DAG `batch_processing_demo` (переключатель слева) и запустить вручную (кнопка "Trigger DAG").
3. В Grid/Graph-view посмотреть на прохождение: `read_source` → `check_condition` → ветка `handle_failures` (жёлтая "up_for_retry" → зелёная на 3-й попытке) → `join` → `notify_success`.
4. Открыть **http://localhost:8025** (MailHog) — увидеть письмо об успехе.
5. Чтобы показать сценарий с ошибкой: в Airflow UI зайти в **Admin → Variables**, добавить `force_fail` = `true`, снова запустить DAG вручную. Ветка `handle_failures` исчерпает все retry и упадёт, вместо `notify_success` сработает `notify_failure` — письмо об ошибке появится в MailHog.
