### **Функциональные требования**

| № | Действующие лица или системы | Use Case | Описание |
| :-: | --- | --- | --- |
| 1 | Сотрудник склада | Загрузка отчёта | Пользователь загружает CSV отчёт через веб-интерфейс. |
| 2 | Монолит (UI/API) | Сохранение файла | Файл сохраняется в GCS, создаётся запись задания на обработку. |
| 3 | Batch ETL Service (Spring Batch) | ETL обработка | Сервис читает CSV, валидирует, обогащает данными из БД (справочники/loyality_data) и пишет в результирующую таблицу. |
| 4 | Batch ETL Service | Уведомление о результате | По завершении обновляет статус обработки (успех/ошибка) для UI/поддержки. |
| 5 | Аналитики/система отчётности | Получение данных | Данные в результирующих таблицах используются для дашбордов/аналитики. |

### **Нефункциональные требования**

| № | Требование |
| :-: | --- |
| 1 | Обработка до 400k строк/сутки, в пики 2–3× |
| 2 | Стабильность под ростом (100–150 параллельных загрузок в пиковые часы) |
| 3 | Среднее время обработки отчёта на 2000 строк — до 30 секунд (цель) |
| 4 | Надёжность: retry/skip для транзиентных ошибок, возможность рестарта job |
| 5 | Наблюдаемость: централизованные логи и метрики выполнения job/step |
| 6 | Cloud-ready: деплой рядом с микросервисами, секреты/конфиги, горизонтальное масштабирование |

### **Решение**
Внедряем отдельный компонент Batch ETL Service на Spring Batch.
- Монолит выполняет только приём файла, валидацию формата на базовом уровне и сохранение в GCS.
- Batch ETL Service выполняет пакетную обработку:
   - chunk-based запись (снижение транзакционных накладных расходов),
   - restartability через BATCH_* метаданные,
   - retry/skip политики (при необходимости),
   - возможность масштабирования (несколько реплик сервиса + распределение заданий через очередь/таблицу задач).

Для POC реализован ETL:
- input: product-data.csv
- enrich: чтение discount по loyalty_code из таблицы loyality_data
- output: upsert в products с вычислением final_price

### **Альтернативы**
1) Kubernetes CronJob + Python/Go ETL
- Плюсы: просто, дешево, быстро прототипировать.
- Минусы: меньше “batch semantics” из коробки (restartability/step metadata), сложнее поддерживать при росте логики.

2) Airflow/Dagster как оркестратор
- Плюсы: мощная оркестрация, интеграции, UI.
- Минусы: отдельная платформа, избыточно для локального ETL внутри Java-стека; саму обработку всё равно надо писать.

3) SQL stored procedures / триггеры
- Плюсы: скорость для простых операций.
- Минусы: сложная поддержка бизнес-логики/версионирования/тестирования; хуже наблюдаемость.

4) Стриминг (Kafka + consumers)
- Плюсы: near-real-time обработка.
- Минусы: входные данные в виде файлов; требования допускают ночную пакетную обработку; усложнение платформы.

**Недостатки, ограничения, риски**
- Требуется дисциплина управления заданиями (идемпотентность, конкуренция, “один файл — один job”).
- Рост параллельных загрузок потребует очереди/таблицы задач и лимитов конкуренции (чтобы не перегрузить БД).
- Наблюдаемость потребует внедрения метрик/логирования (планируется в следующих задачах).
