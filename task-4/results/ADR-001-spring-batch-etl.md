# ADR-001: Spring Batch как ETL-решение для обработки складских отчётов TradeWare

### **Название задачи:**

## Функциональные требования

|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :-: | :- | :- | :- |
|1|Сотрудник склада, ERP-интерфейс|Загрузка отчёта об остатках|1. Сотрудник формирует отчёт по Excel-шаблону и сохраняет его как CSV.<br>2. Загружает файл через ERP-интерфейс в конце смены.<br>3. Файл сохраняется в файловое хранилище (GCS).<br>4. Запускается ETL-обработка файла.<br>5. По завершении сотрудник получает уведомление о результате.|
|2|ETL-сервис|Валидация формата и целостности данных|1. ETL-сервис читает CSV-файл.<br>2. Проверяет структуру и типы данных каждой строки.<br>3. Некорректные строки пропускает с записью в лог (до заданного лимита), не останавливая загрузку.<br>4. При превышении лимита ошибок завершает джобу со статусом FAILED.|
|3|ETL-сервис, БД справочников|Обогащение позиций справочными данными|1. Для каждой позиции отчёта ETL-сервис ищет запись в таблице `loyality_data` по `productSku`.<br>2. При наличии записи подставляет актуальное значение программы лояльности в позицию.<br>3. При отсутствии — оставляет исходное значение из отчёта.|
|4|ETL-сервис, БД номенклатуры|Пакетная запись в результирующую таблицу|1. Обогащённые позиции группируются в чанки по 100 записей.<br>2. Каждый чанк вставляется в таблицу `products` одной транзакцией.<br>3. При сбое транзакция чанка откатывается целиком, джоба может быть перезапущена с точки останова.|
|5|ETL-сервис|Учёт выполнения джоб|1. Сервис фиксирует каждый запуск в Job Repository (статус, длительность).<br>2. Считает прочитанные/записанные/пропущенные строки.<br>3. По завершении логирует итоговое содержимое `products` для верификации.|
|6|Менеджер, партнёр|Просмотр актуальных остатков|1. Менеджер открывает ERP-интерфейс.<br>2. Система читает обновлённую таблицу `products`.<br>3. Отображаются актуальные остатки и условия лояльности.|

## Нефункциональные требования

|**№**|**Требование**|
| :-: | :- |
|1|Производительность: отчёт на 2 000 строк обрабатывается в среднем до 30 секунд|
|2|Нагрузка: 100–150 параллельных загрузок в пиковые часы; возможность гибкого масштабирования|
|3|Объём: до 400 000 строк в сутки, в пиковые дни — в 2–3 раза больше|
|4|Надёжность: retry/restart джобы с точки останова; сбой на строке N не требует повторной обработки всего файла|
|5|Устойчивость к данным: отдельные битые строки не должны ронять загрузку целиком|
|6|Наблюдаемость: централизованный сбор логов и метрик ETL-процесса (задания 5–6)|
|7|Совместимость со стеком команды: Java, Spring, PostgreSQL, GCP|
|8|Готовность к микросервисной архитектуре: ETL-компонент — отдельный сервис, развёрнутый рядом с монолитом|

## Решение

### Выбранное решение: **Spring Batch** (отдельный Spring Boot-сервис пакетной обработки)

### Диаграмма контекста (C4 — System Context)

- [diagrams/c4-context.puml](./diagrams/c4-context.puml)

Система TradeWare как «чёрный ящик»: сотрудники складов и партнёры передают CSV-отчёты и получают актуальные остатки; файлы отчётов хранятся во внешнем облачном хранилище GCS. Пакетная обработка отчётов — внутренняя ответственность системы.

### Диаграмма контейнеров (C4 — Container)

- [diagrams/c4-container.puml](./diagrams/c4-container.puml)

Основные компоненты и интеграции:

- **ETL Batch Service** (Java 17, Spring Boot 3, Spring Batch) — джоба `importProductJob` из одного чанк-шага: `FlatFileItemReader` читает `product-data.csv`, `ProductItemProcessor` обогащает позицию из `loyality_data` (параметризованный запрос по `productSku`), `JdbcBatchItemWriter` пишет в `products` пакетами по 100 записей в одной транзакции на чанк. Fault-tolerant-конфигурация: до 10 битых строк пропускаются с записью в лог.
- **Products DB** (PostgreSQL) — таблицы `products`, `loyality_data`, а также метаданные `BATCH_*` (Job Repository: история запусков, статусы, счётчики read/write/skip).
- **Файловое хранилище** (GCS в целевой схеме; classpath-файл в POC) — источник CSV-отчётов.
- **JobCompletionNotificationListener** — фиксирует статус, длительность джобы и итоговое содержимое `products`.

POC поднимается локально через `docker compose` (PostgreSQL 15 + приложение); схема таблиц и справочник лояльности создаются скриптом `init-db/01-schema.sql` при первом старте БД.

### Логика выбора

1. **Chunk-обработка снимает ключевую проблему кейса** (НФТ-1, НФТ-3): вместо построчных INSERT, перегружающих транзакционные ресурсы, — пакетная вставка по 100 записей в одной транзакции.
2. **Retry/skip/restart из коробки** (НФТ-4, НФТ-5): Job Repository хранит состояние выполнения, джоба перезапускается с точки останова; битые строки пропускаются без остановки загрузки. В простом скрипте это пришлось бы писать вручную.
3. **Совпадение со стеком и экспертизой команды** (НФТ-7): Java + Spring + JDBC — тот же CI/CD, те же навыки; инжиниринг-лид уже имеет опыт Spring Batch.
4. **Шаг к микросервисам** (НФТ-8): ETL сразу оформляется отдельным Spring Boot-сервисом, который позже получает REST API запуска джоб (задание 6).
5. **Наблюдаемость без смены фреймворка** (НФТ-6): метрики джоб публикуются через Micrometer/Actuator в Prometheus, логи — в ELK (задание 5).
6. **Масштабирование** (НФТ-2): на текущих объёмах — реплики сервиса; при росте — remote chunking/partitioning без смены технологии.

## Альтернативы

### Apache Airflow

Оркестратор пайплайнов на Python (DAG, планировщик, UI).

- **Плюсы:** богатый UI мониторинга, cron/sensors/ветвления, нативный запуск в Kubernetes, большая экосистема провайдеров — сильный кандидат при появлении сложных пайплайнов с несколькими источниками данных, которые TradeWare планирует.
- **Минусы:** это оркестратор, а не ETL-движок — саму обработку всё равно придётся писать отдельно; Python-стек вне экспертизы команды (НФТ-7); постоянный overhead инфраструктуры (scheduler + webserver + metadata DB); избыточен для линейного сценария «CSV → обогатить → PostgreSQL».
- **Почему отклонён:** не закрывает задачу обработки сам по себе и не соответствует стеку команды. Может быть добавлен позже **как оркестратор поверх** Spring Batch-джоб.

### Apache Spark

Распределённый движок обработки данных.

- **Плюсы:** настоящий параллелизм, масштабирование на петабайты, отказоустойчивость из коробки.
- **Минусы:** явный overkill для 400 тыс. строк/сутки; требует развёртывания и сопровождения Spark-кластера; высокий порог входа; окупается только при росте объёмов на порядки.
- **Почему отклонён:** переусложнение архитектуры без выигрыша на текущих и прогнозируемых объёмах (НФТ-3).

### K8s CronJob + собственный скрипт

Контейнер со скриптом обработки, запускаемый по расписанию.

- **Плюсы:** просто, дёшево, нативно для Kubernetes.
- **Минусы:** нет restart с точки останова (падение на 300 000-й строке = полный перезапуск файла), нет истории запусков и счётчиков, транзакционность и retry придётся реализовывать самим — фактически переизобретение Spring Batch худшего качества; НФТ-4 и НФТ-5 не выполняются.
- **Почему отклонён:** не обеспечивает требуемую надёжность обработки.

## Недостатки, ограничения, риски

**Недостатки:**
1. Нет встроенного горизонтального масштабирования «из коробки» — для 100–150 параллельных загрузок (НФТ-2) потребуется пул реплик сервиса, а при дальнейшем росте — remote chunking/partitioning с брокером сообщений, что требует ручной настройки.
2. Не оркестратор: расписания и зависимости между джобами — забота внешних инструментов.
3. Job Repository добавляет служебные таблицы `BATCH_*` в БД, которые нужно периодически очищать.

**Ограничения:**
1. Обработка выполняется в рамках одной JVM; параллелизм по файлам — только через несколько экземпляров сервиса.
2. Размер чанка — компромисс между числом транзакций и потреблением памяти; оптимум подбирается нагрузочным тестированием.
3. Блокирующий JDBC-процессор обращается к справочнику на каждую строку; при росте объёмов справочник стоит кэшировать в памяти джобы.

**Риски и меры:**
1. *Невыполнение SLA по времени обработки при пиковой нагрузке* (вероятность средняя, влияние высокое) → нагрузочное тестирование на объёмах НФТ-1/НФТ-2, тюнинг размера чанка и пула соединений, индексы по `productSku`.
2. *Деградация PostgreSQL при параллельных джобах* (вероятность средняя, влияние среднее) → ограничение пула одновременных джоб, connection pooling (HikariCP), при необходимости read-реплика для справочников.
3. *Частичная загрузка при сбое* (вероятность низкая, влияние высокое) → транзакционность на уровне чанка + restart с точки останова из Job Repository.
4. *Рост сложности пайплайнов в будущем* (вероятность средняя, влияние среднее) → Airflow может быть добавлен как оркестратор поверх Spring Batch-джоб без отмены текущего решения.
