# ADR-001: Внедрение Spring Batch для ETL-обработки складских отчётов

### <a name="_b7urdng99y53"></a>**Название задачи:**
Миграция процесса обработки CSV-отчётов по складским остаткам на Spring Batch ETL

### <a name="_3bfxc9a45514"></a>**Функциональные требования**

| **№** | **Действующие лица или системы** | **Use Case** | **Описание** |
| :-: | :- | :- | :- |
| 1 | Сотрудник склада | Загрузка CSV-отчёта об остатках | 1. Сотрудник формирует CSV-файл через Excel-шаблон.<br>2. Загружает файл через ERP-интерфейс.<br>3. Система сохраняет файл в Google Cloud Storage.<br>4. Запускается асинхронный ETL-процесс.<br>5. Сотрудник получает уведомление о результате. |
| 2 | ETL-процесс | Валидация формата и целостности данных | 1. Чтение CSV-файла из GCS.<br>2. Проверка структуры и типов данных.<br>3. При ошибке — запись в лог ошибок, пропуск строки (скип).<br>4. Продолжение обработки валидных строк. |
| 3 | ETL-процесс | Обогащение данных справочной информацией | 1. Для каждой строки товара запрос в БД `loyalty_data`.<br>2. Получение программы лояльности, скидки, мультипликатора.<br>3. Расчёт финальной цены с учётом скидки.<br>4. Если данных нет — применение стандартных значений. |
| 4 | ETL-процесс | Сохранение в результирующую таблицу | 1. Пакетная вставка (upsert) обработанных записей в таблицу `products`.<br>2. При конфликте по `product_id` — обновление существующей записи.<br>3. Фиксация времени обработки (`processed_at`). |
| 5 | Менеджер склада | Просмотр актуальных остатков | 1. Открытие ERP-интерфейса.<br>2. Запрос к таблице `products`.<br>3. Отображение остатков с актуальными ценами и скидками. |
| 6 | Система мониторинга | Отслеживание состояния ETL-задач | 1. Сбор метрик выполнения (количество прочитанных/записанных строк).<br>2. Логирование ошибок валидации.<br>3. Алертинг при падении задачи. |

### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**

| **№** | **Требование** |
| :-: | :- |
| 1 | Среднее время обработки отчёта на 2000 строк — не более 30 секунд. |
| 2 | Поддержка 100–150 параллельных загрузок в пиковые часы без деградации времени ответа API. |
| 3 | Горизонтальная масштабируемость: возможность запуска дополнительных экземпляров batch-воркеров при росте нагрузки в 2–3 раза. |
| 4 | Отказоустойчивость: повторная обработка (retry) при временных сбоях БД или GCS, пропуск (skip) битых строк без остановки всего процесса. |
| 5 | Идемпотентность: повторная загрузка одного файла не приводит к дублированию данных (upsert). |
| 6 | Централизованный сбор логов и метрик с возможностью алертинга при аномалиях. |
| 7 | Совместимость с текущим стеком: Java 11+, PostgreSQL, Google Cloud Platform. |
| 8 | Подготовка к микросервисной архитектуре: ETL-компонент должен быть независимым сервисом. |
| 9 | Асинхронность: загрузка файла пользователем не блокирует интерфейс ERP. |
| 10 | Соответствие модели данных: сохранение всех полей из CSV + обогащённых данных лояльности. |

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

#### Альтернатива 1: Apache Spark (распределённая обработка)

| Критерий | Оценка |
|----------|--------|
| **Описание** | Использование Apache Spark для распределённой обработки CSV-файлов на кластере. Поддерживает batch- и streaming-режимы. |
| **Преимущества** | • Линейная масштабируемость на миллиардах строк данных.<br>• Встроенная поддержка параллелизма и отказоустойчивости (RDD, DataFrames).<br>• Нативная интеграция с GCS через Hadoop коннектор.<br>• Высокая производительность за счёт in-memory вычислений.<br>• Богатый API для трансформации данных (Spark SQL, MLlib). |
| **Недостатки** | • **Избыточен для текущих объёмов:** 400K–1.2M строк/сутки не требуют распределённой обработки.<br>• **Сложность инфраструктуры:** требует развёртывания и администрирования Spark-кластера (YARN/Kubernetes).<br>• **Технологический разрыв:** стек Scala/Python, команда работает на Java. Обучение займёт 1–2 месяца.<br>• **Стоимость:** кластер из 3+ нод даже в минимальной конфигурации — $500+/мес на GCP.<br>• **Overengineering:** внедрение Spark для текущих задач — как использовать заводской станок для забивания гвоздей. |
| **Когда стоит пересмотреть** | При росте объёмов данных до 10M+ строк/сутки или появлении требований к сложной аналитике (агрегации, ML). |
| **Причина отклонения** | Переусложнение архитектуры на текущем этапе. Неоправданные затраты на инфраструктуру и обучение. |

---

#### Альтернатива 2: Apache Airflow + Python (оркестрация ETL)

| Критерий | Оценка |
|----------|--------|
| **Описание** | Apache Airflow для планирования, оркестрации и мониторинга ETL-пайплайнов. Логика обработки на Python (pandas). |
| **Преимущества** | • **Гибкое планирование:** cron-выражения, зависимости между задачами, повторные запуски.<br>• **Визуальный мониторинг:** веб-интерфейс с графом DAG, историей запусков, логами.<br>• **Большое сообщество:** множество готовых операторов (GCS, Postgres, Slack).<br>• **Управляемый сервис в GCP:** Cloud Composer (хотя и дорогой).<br>• **Хорош для сложных пайплайнов:** когда ETL состоит из 10+ зависимых шагов. |
| **Недостатки** | • **Добавляет Python в Java-стек:** увеличивает «технологический зоопарк». Команде придётся поддерживать код на двух языках.<br>• **Требует отдельной инфраструктуры:** веб-сервер, scheduler, workers, база метаданных Airflow.<br>• **Избыточен для простого ETL:** текущая задача — линейная обработка файла (Read → Process → Write), без сложных ветвлений.<br>• **Кривая обучения:** концепции DAG, Operators, XCom требуют времени на освоение.<br>• **Стоимость Cloud Composer:** ~$300–500/мес за минимальную конфигурацию. |
| **Когда стоит пересмотреть** | При появлении сложных ETL-пайплайнов с множеством зависимых шагов (например, обработка данных из 5+ источников с разным расписанием). |
| **Причина отклонения** | Задача простая (один файл → одна таблица), Airflow добавляет неоправданную сложность. |

#### Альтернатива 3: Kafka + Kafka Streams (потоковая обработка)

| Критерий | Оценка |
|----------|--------|
| **Описание** | Публикация каждой строки CSV в топик Kafka и потоковая обработка через Kafka Streams API. |
| **Преимущества** | • **Обработка в реальном времени:** миллисекундная задержка, данные доступны сразу после загрузки.<br>• **Хорошая масштабируемость:** партиционирование топиков, добавление consumer'ов.<br>• **Event-driven архитектура:** естественно вписывается в микросервисный ландшафт.<br>• **Exactly-once семантика:** гарантии доставки для критичных данных. |
| **Недостатки** | • **Задача batch по своей природе:** файлы загружаются раз в смену, нет потребности в миллисекундной задержке.<br>• **Требует Kafka-кластера:** брокеры (минимум 3), ZooKeeper, администрирование. Стоимость на GCP — $200–400/мес.<br>• **Усложняет обработку целостности файла:** файл — атомарная единица, а Kafka работает с отдельными сообщениями. Придётся реализовывать механизм группировки.<br>• **Высокий порог входа:** команда без опыта Kafka потратит 1–2 месяца на изучение и настройку.<br>• **Избыточная сложность:** для batch-задачи правильнее использовать batch-инструмент. |
| **Когда стоит пересмотреть** | При переходе на событийную архитектуру и появлении требований real-time обновления остатков (например, мгновенное отражение продаж). |
| **Причина отклонения** | Batch-задача должна решаться batch-инструментом. Kafka добавляет значительную сложность без бизнес-необходимости. |

---

#### Альтернатива 4: Google Cloud Dataflow (управляемый сервис)

| Критерий | Оценка |
|----------|--------|
| **Описание** | Полностью управляемый serverless-сервис для ETL на основе Apache Beam. Автоматическое масштабирование под нагрузку. |
| **Преимущества** | • **Нулевое администрирование:** не нужно управлять серверами, кластерами, обновлениями.<br>• **Автомасштабирование:** ресурсы выделяются динамически под объём данных.<br>• **Нативная интеграция с GCP:** GCS, BigQuery, Pub/Sub, Cloud Spanner из коробки.<br>• **Unified модель:** Apache Beam позволяет писать пайплайны, работающие на разных раннерах (Dataflow, Spark, Flink). |
| **Недостатки** | • **Vendor lock-in:** жёсткая привязка к GCP. При миграции в другое облако потребуется переписывание.<br>• **Стоимость:** оплата за vCPU/память и объём обработанных данных. Может быть дороже собственного сервиса на GCE.<br>• **Модель программирования Apache Beam:** требует изучения (PCollection, ParDo, Windowing). Непривычна для разработчиков без опыта Big Data.<br>• **Ограниченный контроль:** сложнее кастомизировать обработку ошибок, retry-логику по сравнению со Spring Batch.<br>• **Отладка:** распределённые пайплайны сложнее отлаживать локально. |
| **Когда стоит пересмотреть** | При взрывном росте данных (100M+ строк/сутки) и желании полностью избавиться от управления инфраструктурой. |
| **Причина отклонения** | Дополнительные затраты и vendor lock-in без явных преимуществ перед Spring Batch на текущих объёмах. Компания и так на GCP, но Dataflow избыточен для 1.2M строк. |

#### Альтернатива 5: Ручная реализация ETL на чистом Java

| Критерий | Оценка |
|----------|--------|
| **Описание** | Самостоятельная реализация ETL-процесса с использованием Java NIO, JDBC, пула потоков (ExecutorService) без фреймворков. |
| **Преимущества** | • **Полный контроль:** никаких ограничений фреймворка.<br>• **Отсутствие зависимостей:** не нужно добавлять библиотеки в проект.<br>• **Максимальная гибкость:** любые кастомные сценарии обработки ошибок, логирования, мониторинга. |
| **Недостатки** | • **Изобретение велосипеда:** придётся реализовать chunk-обработку, retry, skip, мониторинг, аудит — всё, что Spring Batch даёт из коробки.<br>• **Высокие трудозатраты:** разработка займёт 2–3 месяца вместо 1–2 недель на Spring Batch.<br>• **Баги и стабильность:** свой код потребует длительного тестирования и стабилизации.<br>• **Сложность поддержки:** новый разработчик будет долго вникать в самописный фреймворк.<br>• **Риски:** высокая вероятность пропустить edge-кейсы (частичная запись, гонки потоков). |
| **Когда стоит пересмотреть** | Никогда. Использование готового проверенного фреймворка всегда предпочтительнее для типповых задач. |
| **Причина отклонения** | Абсолютно неоправданные затраты времени при наличии готового решения (Spring Batch). |

### Недостатки, ограничения, риски

#### Недостатки выбранного решения

| № | Недостаток | Описание |
|:-:|------------|----------|
| 1 | Дополнительная зависимость | ~10 новых зависимостей в проекте (spring-batch-core, spring-batch-infrastructure). При миграции Spring Boot может потребоваться обновление. |
| 2 | Служебные таблицы JobRepository | 6 дополнительных таблиц в PostgreSQL требуют периодической очистки старых выполнений для предотвращения разрастания. |
| 3 | Кривая обучения | Команде потребуется 1–2 недели на изучение концепций: Job, Step, Chunk, JobRepository, ItemReader/Processor/Writer. |
| 4 | Ограниченная гибкость обработки ошибок | Стандартные skip/retry политики не покрывают сложные сценарии (частичное повреждение структуры CSV). Требуются кастомные Processor. |

#### Ограничения

| № | Ограничение | Описание |
|:-:|-------------|----------|
| 1 | Обработка в рамках одного JVM | По умолчанию Spring Batch не распределённый. Для параллельной обработки файлов нужен remote partitioning (JMS/Kafka) или несколько экземпляров с очередью. |
| 2 | Размер чанка — компромисс | Маленький чанк (5) → больше транзакций. Большой (1000+) → больше памяти. Оптимальный размер подбирается эмпирически. |
| 3 | Отсутствие встроенного GCS-ридера | Нужен кастомный ItemReader через Google Cloud Storage Client Library или копирование файла локально перед обработкой. |
| 4 | Не для потоковой обработки | При появлении требований real-time обновления остатков потребуется другой инструмент (Kafka, Debezium). |

#### Риски

| № | Риск | Вероятность | Влияние | Митигация |
|:-:|------|:----------:|:-------:|-----------|
| 1 | **Конфликты при параллельной обработке.** Несколько воркеров обновляют одну запись в `products`. | Средняя | Высокое | • Upsert (`ON CONFLICT DO UPDATE`).<br>• Один файл → один воркер.<br>• Оптимистическая блокировка (`version`). |
| 2 | **Деградация БД при 100+ параллельных задачах.** PostgreSQL не справляется с нагрузкой. | Высокая | Среднее | • Connection pooling (HikariCP, пул 20–50).<br>• Ограничение concurrent задач.<br>• Read replica для `loyalty_data`. |
| 3 | **Потеря данных при сбое в середине обработки.** Частичное обновление `products`. | Низкая | Высокое | • Транзакционность на уровне чанка.<br>• Перезапуск с точки сбоя (JobRepository).<br>• Staging-таблица с атомарным переносом. |
| 4 | **Несовместимость с микросервисной архитектурой.** Batch плохо интегрируется в event-driven. | Средняя | Среднее | • Сразу проектировать как микросервис.<br>• Легковесные Job без зависимостей от монолита.<br>• Асинхронный запуск через очередь. |
| 5 | **Сложность отладки распределённых задач.** Труднее дебажить, чем монолит. | Средняя | Низкое | • ELK/Loki для централизованных логов.<br>• Трассировка (Sleuth + Zipkin).<br>• Таблица `error_records` для анализа. |
| 6 | **Недостаточная производительность в будущем.** При росте до 5–10M строк/сутки. | Низкая | Высокое | • Замеры сейчас для прогноза точки перелома.<br>• Возможность замены batch-слоя без изменения API.<br>• План Б: миграция на Spark/Dataflow. |

### План действий

| Этап | Срок | Результат |
|------|------|-----------|
| 1. POC Spring Batch | 1–2 недели | Работающий прототип ETL для загрузки `product-data.csv` |
| 2. Интеграция с GCS | 1 неделя | Кастомный ItemReader для чтения CSV из Cloud Storage |
| 3. Внедрение мониторинга | 1 неделя | Метрики в Prometheus, дашборд в Grafana |
| 4. Нагрузочное тестирование | 1 неделя | Подтверждение SLA: 2000 строк за ≤30 сек, 100+ параллельных задач |
| 5. Миграция продакшн-процесса | 2 недели | Перевод обработки отчётов с монолита на Batch ETL Service |
| 6. Документирование и обучение | 1 неделя | Внутренняя документация, воркшоп для команды |

**Общий срок:** 7–8 недель до полного внедрения.

### Ревизия решения

Данный ADR подлежит ревизии через **6 месяцев** после внедрения (декабрь 2026) для оценки:

- Фактической производительности в сравнении с SLA.
- Необходимости перехода на remote partitioning.
- Анализа затрат на инфраструктуру.
- Целесообразности миграции на альтернативное решение (Spark/Dataflow) при значительном росте объёмов данных.
