### <a name="_b7urdng99y53"></a>**Название задачи:**
Внедрение пакетной обработки ежедневного отчёта об остатках складов TradeWare с использованием Spring Batch

### <a name="_3bfxc9a45514"></a>**Функциональные требования**

|**№**|**Действующие лица или системы**|**Use Case**|**Описание**|
| :-: | :- | :- | :- |
|1|Сотрудник склада|Загрузка отчёта об остатках|Формирует CSV-отчёт по Excel-шаблону и загружает его через веб-интерфейс ERP. Первичная валидация формата - на уровне шаблона|

|4|Spring Batch Job|Обработка ошибок и повторные попытки|При сбое чтения/обработки отдельного чанка - retry по настраиваемой политике; при исчерпании попыток - шаг помечается как failed, Job можно перезапустить с точки останова (JobRepository хранит состояние), а не с нуля|
|5|Сотрудник склада|Получение уведомления о результате|После завершения Job (успех/ошибка) пользователь получает уведомление в браузере|
|6|Отдел аналитики и отчётности|Чтение обновлённых остатков|Формирует отчёты на основе уже обновлённой таблицы номенклатуры, не создавая дополнительную нагрузку на транзакционные ресурсы в момент загрузки файла (данные обновляются пакетно, а не запросами в реальном времени)|
|7|Логистические партнёры / региональные склады|Вызов API остатков|Работают с тем же API, но оно больше не блокируется потоком построчных апдейтов от загрузки отчётов - обработка отчёта вынесена в отдельный batch-процесс с собственным пулом ресурсов|

### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
|1|Обработка отчёта объёмом ~400 000 строк/сутки, в пиковые дни - рост в 2–3 раза|
|2|Поддержка 100–150 параллельных загрузок отчётов в пиковые часы без деградации ERP-интерфейса|
|3|Среднее время обработки отчёта на 2 000 строк - до 30 секунд|

|5|Разделение ресурсов между batch-обработкой отчётов и «горячим» API для партнёров/складов (исключение взаимного блокирования)|

### <a name="_qmphm5d6rvi3"></a>**Решение**

- Пользовательский путь загрузки файла (сотрудник склада → веб-интерфейс → Java-приложение → GCS) **не меняется**, чтобы не трогать рабочий процесс сотрудников на этом этапе.
- После сохранения файла в GCS вместо немедленной построчной обработки внутри того же потока запроса Java-приложение **запускает Spring Batch Job** (изначально как встроенный в тот же монолит компонент, что не требует нового способа развёртывания на старте).
- Job состоит из одного шага с чанк-ориентированной обработкой:
  - **Reader** — `FlatFileItemReader`, построчно читает CSV;
  - **Processor** — обогащает каждую строку данными из `БД справочных данных о товарах` одним обращением на чанк, а не на строку;
  - **Writer** — `JdbcBatchItemWriter`, пишет чанк в `БД номенклатуры` одним batch-запросом вместо построчных INSERT/UPDATE.
- Состояние выполнения Job (какие чанки обработаны, ошибки, статус) хранится в служебных `BATCH_*`-таблицах в той же PostgreSQL - это даёт retry и restart «из коробки» без дополнительной инфраструктуры.
- API для партнёров и региональных складов продолжает читать `БД номенклатуры` напрямую и никак не завязан на процесс загрузки отчёта - построчная блокировка транзакционных ресурсов, которая была, устраняется тем, что запись теперь идёт пакетно и в отдельном потоке выполнения, а не в потоке HTTP-запроса загрузки файла.
- Отчётность для отдела аналитики может быть перенесена на чтение уже готовой таблицы номенклатуры (обновлённой пакетно ночью) вместо расчётов в реальном времени.

**Обоснование выбора Spring Batch:**
- Инженерная команда — Java/WildFly, без опыта в Python/Airflow или Spark; Spring Batch не требует нового языка и ложится поверх существующего Spring монолита.
- Из коробки есть: чанковая обработка (управляет транзакциями и объёмом данных в памяти), retry и skip-политики для шагов, restart с точки останова через `JobRepository`, история выполнений.
- Не требует отдельного кластера/сервиса для старта - можно внедрить внутри уже существующего Java-монолита, а затем вынести в отдельный сервис, что соответствует бизнес-цели компании о постепенной миграции к микросервисам.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

| Решение | Недостатки |
| :- | :- |
| **Apache Airflow** | Оркестратор нескольких разнородных задач по расписанию, но не является ETL-движком. Под капотом нужен код обработки на чём-то (Python/Bash/вызов внешнего джоба). В команде Java-разработчики, поэтому добавление Python-стека ради оркестрации одного пайплайна избыточно на этом этапе.|
| **Apache NiFi** | Визуальный dataflow-инструмент для маршрутизации разнородных протоколов/форматов между системами. Для одной задачи «CSV → обогащение → таблица» это избыточная инфраструктура (свой кластер, свой UI, отдельная эксплуатация), конфигурация в основном декларативная через UI — не сочетается с код-ревью и версионированием. |
| **Кастомный скрипт на Java/JDBC по расписанию (cron / k8s CronJob)** | Минимальный footprint, знакомый стек, но retry, chunking, restart с точки останова, метаданные о выполнении придётся писать и поддерживать вручную. Spring Batch даёт это «из коробки».|
| **GCP Dataflow (Apache Beam)** | БД и файлы уже в GCP, даёт автомасштабирование и managed-инфраструктуру, но требует переписать логику под модель Beam (PCollection/Transform), новую для команды парадигму, и полноценного отрыва от монолита прямо сейчас — то есть не «локально развёрнутое решение», которое можно продемонстрировать и внедрить постепенно, а рывок в облачный managed-сервис. Как вариант для второй волны миграции, когда объёмы вырастут настолько, что одного Spring Batch Job станет недостаточно. |
| **Apache Spark (batch)** | Избыточен для объёма ~400 000–1 200 000 строк/сутки на одну задачу. Это объём, с которым чанковая JDBC-обработка справляется на одной JVM. Spark оправдан при распределённой обработке на кластере для существенно больших объёмов или сложных трансформаций (join'ы многих больших таблиц, ML и т.д.). |

**Недостатки, ограничения, риски выбранного решения**

- **Масштабирование.** Spring Batch по умолчанию выполняет Job в одном JVM-процессе. Чтобы держать 100–150 параллельных загрузок в пиковые часы, потребуется либо запускать несколько экземпляров Job параллельно (partitioning/remote chunking), либо выносить обработку каждого отчёта в отдельный под/процесс — это дополнительная работа по конфигурации, не решаемая «из коробки» одной аннотацией.
- **Служебные таблицы в БД.** `JobRepository` создаёт и использует таблицы `BATCH_*` в той же PostgreSQL, что и бизнес-данные - дополнительная связанность и нагрузка на ту же БД, которая и так испытывает пиковую нагрузку; при неудачном выборе chunk-size это может создать новые узкие места вместо решения старых.
- **Подбор размера чанка под SLA.** Требование 2 000 строк ≤ 30 секунд и рост нагрузки в 2–3 раза в пик потребуют нагрузочного тестирования и подбора `chunk size`/размера транзакции, т.к. без этого решение не гарантирует соблюдение SLA автоматически.
- **Идемпотентность шагов.** Restart с точки останова полезен только если шаги идемпотентны. Это требует дисциплины при написании writer'а (upsert вместо чистого insert), иначе retry может привести к рассинхронизации данных.
- **Не решает проблему целиком.** Spring Batch закрывает конкретно пакетную ETL-обработку отчёта об остатках. Мониторинг/алертинг и решение по трейсингу Spring Batch сам по себе не покрывает, только предоставляет точки интеграции (Actuator/Micrometer).
- **Локальное развёртывание.** Текущий POC - однономодовый запуск через Docker Compose на локальной машине. Полноценный перенос в GCP потребует отдельного компонента для планирования и запуска Job по расписанию (например, Cloud Scheduler совместно с Cloud Run/GKE Job) - этот компонент в архитектуре решения не проработан и потребует отдельного проектирования.
