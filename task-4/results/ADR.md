# ADR: Выбор Spring Batch для ETL-обработки складских отчетов

## Контекст

TradeWare обрабатывает до 400 000 строк CSV-отчетов в сутки (до 1.2 млн в пиковые периоды). Текущая система обрабатывает записи построчно в онлайн-режиме, что перегружает транзакционные ресурсы БД и приводит к задержкам в обновлении остатков.

Требуется ETL-решение, которое:
- Пакетно обрабатывает CSV-файлы (чтение, обогащение из справочников, запись в БД)
- Обрабатывает отчет на 2 000 строк за 30 секунд
- Выдерживает 100-150 параллельных загрузок в пиковые часы
- Интегрируется с существующей Java-экосистемой (Java 11, WildFly, PostgreSQL)
- Поддерживает retry, мониторинг и масштабирование

## Рассмотренные варианты

### 1. Spring Batch (выбран)

Фреймворк для пакетной обработки данных в Java-экосистеме. Модель Reader-Processor-Writer с chunk-based processing, транзакционностью и restart/retry из коробки.

Плюсы:
- Нативная интеграция с Java-стеком команды (Java, Spring, JDBC, PostgreSQL)
- Chunk-based processing снижает нагрузку на БД: данные вставляются пакетами, а не построчно
- Встроенный retry (`retryLimit`, `skip`), restart с точки останова, транзакционность на уровне chunk
- Job Repository хранит историю запусков, статусы, метрики
- Легко интегрируется с Spring Boot Actuator и Micrometer для мониторинга
- Деплоится как обычное Spring Boot приложение - тот же CI/CD, те же навыки команды

Минусы:
- Требует JVM (256-512 MB RAM базово)
- Не является оркестратором - для сложных зависимостей между Job-ами нужен внешний инструмент
- Конфигурация Job/Step/Reader/Writer избыточнее, чем скриптовые решения

### 2. Apache Airflow

Оркестратор пайплайнов на Python с DAG, планировщиком и UI.

Плюсы:
- Мощный UI для мониторинга и управления
- Встроенный CRON, Sensors, ветвление
- Большая экосистема провайдеров

Минусы:
- Python-стек - не совпадает с Java-экосистемой команды
- Airflow - оркестратор, а не ETL-фреймворк: для самой обработки данных все равно нужен скрипт/приложение
- Высокая ресурсоемкость (Scheduler + Webserver + Metadata DB постоянно)
- Избыточен для задачи "прочитать CSV, обогатить, записать в БД"

### 3. K8s CronJob + скрипт

Контейнер со скриптом, запускаемый по расписанию.

Плюсы:
- Минимальная ресурсоемкость, простота
- Нативная интеграция с K8s

Минусы:
- Нет встроенного retry с точкой продолжения (restart)
- Нет chunk-based транзакционности
- Нет Job Repository для истории и метрик
- При ошибке на строке 300 000 из 400 000 - придется перезапускать с начала
- Не масштабируется для сложных ETL-сценариев

### 4. Apache Spark

Движок распределенной обработки данных.

Плюсы:
- Нативный параллелизм, обработка петабайтов

Минусы:
- Избыточен для 400K строк CSV
- Требует Spark-кластера (Dataproc, Spark Operator)
- Высокий overhead: Driver + Executor, минимум 1-2 GB
- Сложность операционного обслуживания

## Решение

Выбран Spring Batch как ETL-фреймворк для пакетной обработки складских отчетов.

## Обоснование

1. Соответствие Java-экосистеме. Команда разрабатывает на Java, использует Spring-совместимый стек. Spring Batch не требует изучения нового языка или парадигмы.

2. Chunk-based processing решает ключевую проблему. Текущая построчная обработка перегружает БД. Spring Batch группирует записи в chunk-и (например, по 100 строк) и вставляет одной транзакцией, снижая нагрузку на PostgreSQL.

3. Надежность при больших объемах. При обработке 400K строк критически важен restart с точки останова. Если Job упал на строке 300K, Spring Batch возобновит обработку с 300K+1, а не с начала. Это невозможно в простых скриптах.

4. Мониторинг. Job Repository хранит историю всех запусков, статусы Step-ов, количество прочитанных/записанных/пропущенных записей. Это закрывает потребность в наблюдаемости без отдельной системы.

5. Путь к микросервисам. Spring Batch Job деплоится как Spring Boot микросервис. По мере миграции монолита, ETL-компонент уже будет отдельным сервисом с REST API для запуска Job-ов.

## Последствия

- Команде необходимо освоить Spring Batch API (Job, Step, ItemReader, ItemProcessor, ItemWriter)
- Необходимо выделить ресурсы JVM (рекомендуется 512 MB - 1 GB для обработки пиковых объемов)
- Job Repository требует таблицы в БД (Spring Batch создает их автоматически при `spring.batch.jdbc.initialize-schema=always`)
- В перспективе можно добавить Airflow как оркестратор поверх Spring Batch Job-ов, если появятся сложные зависимости между пайплайнами
