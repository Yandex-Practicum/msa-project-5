# ADR: Spring Batch для ETL TradeWare (задание 4)

## Функциональные требования

| № | Участники | Use case | Описание |
|---|-----------|----------|----------|
| 1 | Склад, ERP | Загрузка CSV остатков | Файл валидируется, обогащается справочниками, пишется в БД пакетно |
| 2 | PostgreSQL | Хранение номенклатуры | Результирующая таблица `products` |

## Нефункциональные требования

| № | Требование |
|---|------------|
| 1 | Не перегружать OLTP: вынести обработку в batch (chunk), повторяемость шагов |
| 2 | Соответствие Java-экосистеме компании |
| 3 | Локальный запуск в Docker, дальше — облако |

## Решение

- **Spring Batch** как слой ETL: `FlatFileItemReader` → `ItemProcessor` (обогащение из `loyality_data`) → `JdbcBatchItemWriter` в `products`.
- **C4 (контейнеры):** пользователь/ERP → Spring Batch (Docker) → PostgreSQL; CSV из classpath как POC.

Соответствует теории спринта: ETL, chunk-oriented processing, `JobRepository` для состояния.

## Альтернативы

| Вариант | Комментарий |
|---------|-------------|
| Apache Airflow | Сильнее для множества источников и DAG; избыточно, если ETL только Java и один сценарий |
| Ручной JDBC в монолите | Уже вызывает деградацию при больших объёмах |
| Spark | Избыточно для CSV на тысячи строк |

## Риски и ограничения

- Нужна отказоустойчивость **JobRepository** (PostgreSQL).
- Для миллионов строк — partitioning / параллельные шаги (см. теорию Spring Batch).
